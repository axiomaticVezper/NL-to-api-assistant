Especially important: a planner proposing `POST /approvals/{id}/approve` would be trying to approve its own work (the server blocks it, but it should never be proposed).

\## The governed flow



```

POST /plans            -> server decides tier + approval need   -> pending\_approval (or approved if low risk)

POST /approvals/{id}/approve | reject                           -> approver/admin decides

<the real endpoint>    + X-Plan-Id + Idempotency-Key            -> executes once

GET  /audit?plan\_id=   -> full timeline

```



\## New endpoints



| Endpoint | Who | Purpose |

|---|---|---|

| `POST /plans` | any logged-in user | Submit a `Plan` (the shared contract). Returns `plan\_id`, `status`, `risk\_tier`, `requires\_approval`. |

| `GET /plans/{plan\_id}` | requester, approver, admin | View a plan and its decision. |

| `GET /approvals` | approver, admin | Pending plans this role may decide. |

| `POST /approvals/{plan\_id}/approve` / `reject` | approver, admin | Body: `{"note": "..."}` (optional). |

| `GET /compensations` | any logged-in user | Which actions can be undone, and how. |



\## Rules the server enforces (it ignores what the client claims)



\- \*\*The server decides\*\* the real risk tier, whether approval is needed, the status, and `requested\_by` (taken from the token). If a submitted `risk\_tier` does not match the server's, the plan is rejected with 422 and logged.

\- \*\*Approval is required\*\* for `high\_risk\_write` and `critical\_write`. Read-only and low-risk plans are cleared immediately and can call their endpoint directly, as before.

\- \*\*Who decides:\*\* `high\_risk\_write` by approver or admin. `critical\_write` by admin only. Nobody decides their own plan, and a plan is decided once.

\- \*\*An approved plan is a one-time ticket.\*\* It works only for the person who requested it, only for the exact endpoint + method, and only for the exact path parameters it was approved with.

\- `plan\_id` is generated by the server if you omit it. Re-submitting an existing `plan\_id` returns 409.



\## Status codes you will see



| Code | Meaning |

|---|---|

| 428 | High-risk/critical endpoint called without `X-Plan-Id`. |

| 403 | Role not allowed; plan belongs to someone else; plan approved for a different endpoint or ids; unknown plan. |

| 409 | Plan not approved yet / rejected / already used; or already decided. |

| 422 | Plan submission with unknown endpoint or wrong risk tier; or `Idempotency-Key` reused for a different request. |



\## Idempotency



Send `Idempotency-Key: <unique string>` on writes. Same key + same request returns the original result with `Idempotent-Replay: true` and does not run the action again. Keys are per user and last 24 hours. Only successful (2xx) results are remembered, so a failed attempt can be retried with the same key. Retrying an already-executed plan WITH the same key returns the original success; WITHOUT a key it returns 409.



\## Compensating actions (for rollback)



`app/compensation.py` (also `GET /compensations`) lists how each write is undone: refund and reverse-refund undo each other, and adding/removing a team member undo each other. Not undoable (with reasons): delete customer, cancel subscription, change plan (needs the previous value captured first), create ticket. An undo is not run directly. It becomes a new plan that goes through approval like any other action, so undoing a refund is `critical\_write` and needs two admins.
